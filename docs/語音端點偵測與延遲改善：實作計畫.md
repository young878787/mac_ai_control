# 語音端點偵測與延遲改善

狀態（2026-11-04）：Phase 0～3 已完成並以合成語料驗收（13 項全數通過；P1 門檻經使用者於 2026-11-05 核可改為平均 < 2ms）；**Phase 4 真人實測待錄音**。

## 1. 要解決的問題

| 問題 | 原因 |
|---|---|
| 說完話到執行約 2 秒 | server 用能量 VAD 靜音 1.5s 才斷句，再加 `endAudio` 前固定等 0.4s |
| VAD 有時停不下來 | server 的底噪估計只能往下調；環境音在說話中途變大後，每一幀都被當成語音，要等 300s 上限才收（`macos-stt/src/macos_stt/session.py` 的 `VAD.update`） |

## 2. 架構

端點判斷放在 mac_ai（client）端；macos-stt 只新增「client 要求 flush」與計時欄位，原本的能量 VAD 保留為備援。

```
mic(32ms 幀) ─┬─▶ WS binary（每 96ms 合成一則）──▶ macos-stt Session.feed
              └─▶ SileroVad ─▶ EndpointDetector ─▶ WS {"type":"flush"} ─▶ Session.flush()
partial 事件 ────────────────▶ EndpointDetector（語意完整度＋ASR 輔助）
final 事件（帶 timing）──────▶ logs/latency.jsonl ─▶ 執行指令
```

為什麼放在 client：判斷要用的訊號（麥克風原始音訊、partial、Fast Path 詞典）都在 mac_ai；macos-stt 的 pyobjc venv 不必裝 onnxruntime；同一條 WS 連線有順序保證，flush 一定排在最後一幀音訊之後。

端點判斷規則（`mac_ai/stt/endpoint.py`，純邏輯、可離線測試）：

1. **神經網路 VAD＋遲滯**：Silero VAD v5 每 32ms 一窗；連續 3 窗 ≥ 0.5 才算開始說話（單一突波不算），說話中掉到 < 0.35 才算停（進出門檻不同）。
2. **語意端點**：`mac_ai/stt/completeness.py` 把 partial 分成 complete（每個子句都命中 Fast Path 且句尾不是接續詞）／incomplete（句尾是「然後、和、把、到…」或只有動詞沒受詞）／unknown，靜音門檻分別為 0.35s／1.6s／0.8s。
3. **引擎反應保護**：complete 的快速路徑（0.35s）只在「說完之後 partial 更新過」才啟用；否則要等 0.6s。原因：SFSpeechRecognizer 的 partial 比語音晚 0.3～0.6s，句中停頓時舊文字（例如「打開Safari」）早已「穩定」，不擋的話會把後面的「然後搜尋天氣」切掉。
4. **ASR 輔助**：VAD 說在說話但 partial 超過 1.2s 不變 → 當成噪音，靜音從 partial 最後一次變動算起（句中停頓後重新開口的，從重新開口起算）；開口 2.0s 仍沒有任何文字 → 放棄這一段、不送 flush；一句超過 10s → 強制 flush。
5. 送出 flush 後，partial 視為上一句的，直到收到 final（最多等 3s）。

- 依賴：mac_ai 的 `.venv` 新增 `onnxruntime`（1.31.1）；Silero 模型放 `AI_models/silero_vad.onnx`（2,327,524 bytes，sha256 `2623a2953f6ff3d2c1e61740c6cdb7168133479b267dfef114a4a3cc5bdd788f`，`*.onnx` 已被 `.gitignore`，下載方式寫在 README）。
- 驗收數值：採用 §7 的提議值（S1 ≤ 0.8s／p90 ≤ 1.2s、Q1 ≥ 95%、Q3 合成 0／真人 ≤ 1）。

## 6. Log 與指標

`logs/latency.jsonl`（每句一筆，實測樣本）：
```json
{"mode":"client","reason":"complete","class_at_endpoint":"complete","partial_at_endpoint":"關掉Safari",
 "final_text":"關掉Safari","server":{"reason":"client_flush","pre_delay_ms":0.0,"finish_ms":56.6},
 "e2e_ms":414.0,"endpoint_ms":352.2,"finalize_ms":61.2,"vad_ms_mean":0.7, "...":"speech_start/speech_end/endpoint_at/flush_sent/final_recv 為單調時鐘秒數"}
```

| 指標 | 意義 |
|---|---|
| E2E | 說完 → 收到 final（體感延遲；bench 以音檔裡已知的說完時間點為準） |
| endpoint_ms | 說完 → 端點判斷出手 |
| finalize | server 的 pre_delay + endAudio→final（取自 final 的 `timing`，兩種模式都有，可直接比較） |
| `reason` | `complete`／`default`／`incomplete`／`asr_stall`／`max_len`／`server_vad`（備援） |

server 端：`/tmp/macstt_server.log` 的 `[flush] reason=...` 行。

## 8. 與原計畫的差異與實測發現

1. **partial 比語音晚 0.3～0.6s**：E2E ≈ partial 延遲 + 穩定等待 + pre_delay + finish，這是速度的下限，所以新增「引擎反應保護」（§2-3）。
2. **合成語料重做**：原本用 Eddy／Sandy 等語音，Apple STT 本來就聽不懂（`打開碗盤`、整段空白），量到的是 TTS 品質而不是端點；改為只用 Meijia、以語速製造變化。C 類改成一半「噪音在說話中途才出現」，這才重現了 baseline 的 VAD 問題（C 類 2/6 正確）。
3. 發現並修正**句中停頓後重新開口被誤判成噪音**的設計缺陷（ASR 停滯要從重新開口起算），有回歸測試。
4. 順便修了 macos-stt 的 Timer 執行緒洩漏（§4 Phase 1）。
5. 送出合併為 96ms（原計畫沒有），因為每則 WS 訊息在 server 都有固定開銷；實測合併前 macos-stt CPU 比 baseline 高約 5.6pt。

## 9. 風險與已知限制

- **合成語音不能代表真人**：合成語料用於回歸與調參，最終以 Phase 4 為準。
- **多步驟長句中間停頓超過約 0.4s 會被拆成兩句**（E03「關掉 Safari，然後靜音」實測發生）。Fast Path 下兩個 final 各自執行，結果與整句相同；但交給 LLM 的長句會失去整句脈絡。這是「早收」的固有取捨，若真人實測覺得困擾，可調高 `EP_SILENCE_COMPLETE_S`。
- `EP_FLUSH_PRE_DELAY_S = 0` 依賴「flush 只在 partial 已更新後才發」；走 `default`／`incomplete` 路徑（交給 LLM 的句子）沒有這個保證，Phase 4 要特別檢查句尾字。
- 用 partial 提前執行指令（可再省掉 flush→final 的 ~55ms）、SpeechAnalyzer、修 macos-stt 能量 VAD 的底噪鎖死（現由 client 端兜底）、`RESTART_DELAY`：**不在本次範圍**。
- flush 期間 server 的 feed 會被擋（finish + 重開約 0.4s）：下一句的音訊在 WS 裡排隊不會遺失，只記錄不處理。
- macos-stt 是獨立 repo，本次的改動尚未 commit。

## 10. 回退方式

`config.py` 的 `ENDPOINT_MODE = "server"` 即回到舊行為（舊的幀長、靜音 1.5s、pre_delay 0.4，且不載入 VAD）。macos-stt 的改動都是新增功能，舊 client 不帶新欄位時行為不變。
