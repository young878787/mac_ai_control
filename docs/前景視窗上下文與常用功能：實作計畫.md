# 前景視窗上下文與常用功能（Fast／Slow Path 擴充）

狀態：P0–P4 已實作（2026-11-14，基準 HEAD `f70115c`，尚未 commit）。實作結果與尚未驗證的項目見 §13。

## 1. 要解決的問題

現在句子沒指定對象時，一律用固定預設：搜尋開預設瀏覽器的 Google、專案用 Visual Studio Code、「開終端機」開 Terminal.app。使用者其實正看著某個視窗，對象應該由它決定。

| 使用者正在看 | 說 | 現在 | 目標 |
|---|---|---|---|
| Safari 的 Facebook | 查貓咪專頁 | Google 搜尋 | Facebook 站內搜尋 |
| Safari 的 Google 或其他網頁 | 查貓咪 | 預設瀏覽器 Google | 這個瀏覽器 Google |
| Cursor | 打開語音助手專案 | 用 VS Code 開 | 用 Cursor 開 |
| VS Code | 開終端機 | 開 Terminal.app | 開內建終端機面板 |
| 任何 App | 關閉視窗、全螢幕、上一頁… | 交給 LLM（做不到） | 對前景 App 送對應快捷鍵 |

## 2. 已定案的決策（2026-11-14 使用者確認）

| # | 決策 |
|---|---|
| D1 | 站內搜尋直接觸發：停在已知網站說「搜尋／查 X」就用站內搜尋，不必說「在這裡」。例外：句子有即時資訊詞（天氣、新聞…）或網頁範圍詞（上網、google…）時仍走 Google |
| D2 | 「找 X」維持本機優先。本機 0 筆、沒有本機證據、而且前景是瀏覽器時，直接網頁搜尋，不再問 LLM |
| D3 | 編輯器在前景時，「開終端機」開內建終端機面板；使用者明說要獨立的終端機（「終端機程式／App」「獨立終端機」「Terminal」）才開 Terminal.app |
| D4 | 「按鈕」＝各 App 的常用功能，以快捷鍵實作。不做「按下畫面上某個名稱的按鈕」，桌面角色也不加按鈕 |
| D5 | 第一批功能清單（§5.4）與站內搜尋網站（§5.3）照提案 |

對象的優先順序固定為：**句子明說的 → 同句剛開的（`last_browser`／`last_editor`）→ 前景視窗 → 現有預設**。

## 4. 架構

```
match()（純函式，不讀視窗；completeness 熱路徑照舊）
   └─ 回傳「延後決定」的動作：context_search／front_action／open_project／find_file
執行階段（command_worker 執行緒）
   └─ ExecContext.front（惰性：第一次用到才讀，同句快取）
        └─ context.read_front()：lsappinfo → App 名稱；需要網站時才 osascript 問網址
```

## 5. 規格

### 5.1 讀取前景

- 第一段 `lsappinfo`（逾時 `CONTEXT_TIMEOUT_S`）→ App 名稱 → 查 `APP_KIND` 得 `kind`（browser／editor／other）。
- 第二段只在 `kind == browser` 且這個動作需要網站時執行：`osascript` 問該瀏覽器目前分頁網址，只留 host。只支援 Safari、Google Chrome（與 `TAB_BROWSERS` 一致）。
- 前景的 bundle 路徑在本專案目錄底下（桌面角色）、讀取失敗或逾時 → `front = None`，一律退回現有預設行為，不猜。
- 紀錄：`step["context"] = {"app", "host", "site", "used", "ms"}`。不記完整網址，不記視窗標題。

### 5.2 搜尋（`context_search`）

適用：`_r_search` 原本會回 `web_search_or_open_url` 的句子（沒帶 App、沒帶本機範圍詞）。

| 條件（由上往下，第一個成立的採用） | 行為 |
|---|---|
| 句子有網頁範圍詞或即時資訊詞 | Google |
| 同句剛開了瀏覽器（`last_browser`） | 在該瀏覽器 Google（現有行為） |
| 前景是瀏覽器，host 對到 `sites` 且不是 Google | 站內搜尋，用前景瀏覽器開 |
| 前景是瀏覽器，其他網站 | 在前景瀏覽器 Google |
| 其他 | 預設瀏覽器 Google（現有行為） |

結果字串寫明實際對象：`✅ 已在 Facebook 搜尋：貓咪專頁`。關鍵字用使用者原話，不改字。

### 5.3 站內搜尋網站（`sites`）

| 名稱 | host（含子網域） | 搜尋網址 |
|---|---|---|
| Google | `google.com`、`google.com.tw` | `https://www.google.com/search?q={q}` |
| Facebook | `facebook.com` | `https://www.facebook.com/search/top?q={q}` |
| YouTube | `youtube.com` | `https://www.youtube.com/results?search_query={q}` |
| GitHub | `github.com` | `https://github.com/search?q={q}` |

新增網站只改 `vocab/lexicon.json`。

### 5.4 常用功能（`front_action`，`app_shortcuts`）

| 範圍 | 功能 | 說法（例） | 按鍵 |
|---|---|---|---|
| 通用 | 關閉視窗 | 關閉視窗、關掉這個視窗 | 瀏覽器、編輯器、iTerm ⇧⌘W，其他（含 Terminal）⌘W |
| 通用 | 新視窗 | 開新視窗、新視窗 | ⌘N |

規則：

- 比對用完整句 regex，沿用否定／敘述／提問守門。
- 「範圍」不符時不送鍵，回 `⚠️ 目前最前面的是 Finder，這個功能只支援瀏覽器`。
- 送鍵的同一支 `osascript` 先確認前景 App 仍是預期的那個，不是就回 `❌`、不送鍵。
- 只送詞庫表內的按鍵；不打任意文字、不在終端機輸入指令。
- 結束程式、刪除類不在第一批。
- 「新分頁」：前景是 Terminal／iTerm 時送 ⌘T；其他情況維持現有 `browser_tab`。
- 「開終端機」：前景是編輯器時走內建面板；其他情況維持開 Terminal.app。

### 5.5 專案與「找」

- `open_project` 沒指定編輯器時：`last_editor` → 前景編輯器 → Visual Studio Code。
- `find_file` 0 筆且 `local_only` 為 False：前景是瀏覽器 → 直接 `context_search`（D2）；否則維持轉交 LLM。

### 5.6 Slow Path

- 不新增工具。LLM 選 `web_search_or_open_url` 時，瀏覽器依 §2 的優先順序決定（不做站內搜尋，LLM 的 query 可能被改寫）。
- Phase 4：在 user 訊息附 `## 目前視窗\nSafari：facebook.com`。只有 live 對照沒有退步才合併（§9.1 A7）。

### 9.3 真實環境（本機實際執行，由實作者執行並貼出輸出）

`open -a Safari "https://www.facebook.com" && sleep 3 && python main.py --text 查貓咪專頁`。

## 11. 風險與已知限制

- 站內搜尋改變「搜尋＝Google」的習慣，是誤觸發的最大來源；錯判時從 `step["context"]` 追查。

- YouTube 的 `k` 需要焦點在頁面上，焦點在搜尋框時會打出字。
- 讀取前景到送鍵之間使用者若切換 App，靠送鍵前的前景檢查擋下。

### 13.4 與計畫的差異

## 15. 否定／敘述句的誤執行（G1，2026-11-15）

### 15.1 問題與實測

Fast Path 守門把否定、敘述、提問句交給 LLM 判斷語氣，但 4bit 模型幾乎不理會否定。實測 30 句 × 3 次（只規劃不執行）：

| 類別 | 例句 | 該怎麼做 | 改前正確 |
|---|---|---|---|
| A 真否定 | 不要鎖定螢幕、別讓電腦睡眠、不要開小算盤 | 不動作 | 3/33 |
| B 否定即指令 | 不要靜音了、螢幕不要那麼亮 | 照做 | 24/24 |
| C 敘述 | 剛剛鎖定螢幕了、剛才關掉 Safari 了 | 不動作 | 3/18 |
| D 提問 | 要不要鎖定螢幕、鎖定螢幕是什麼意思 | 不動作或回答 | 3/12 |

63 次不該動作中有 27 次是睡眠、鎖定、關閉 App（「別讓電腦睡眠」→ 睡眠，繞過了 Fast Path 睡眠只接受固定句的窄入口）。改系統提示詞：A 仍 3/33、B 降到 12/15；在使用者訊息加提醒：沒有改善。帶「目前視窗」提示（P4）時 C 由 3/18 降到 0/18。

## 16. 常用功能改為底層直接執行（2026-11-15）

### 16.1 問題與決策

送模擬快捷鍵會先經過輸入法：注音啟用時 ⌃`（VS Code 內建終端機）被當成打字，在聊天輸入框打出「、」（§14.6 bug 1）。使用者決定（D13）：全部改用最短、簡潔的底層路徑，統一做法。

### 16.2 分析（唯讀探測，2026-11-15）

| 做法 | 實測 | 結論 |
|---|---|---|
| osascript ＋ System Events 送鍵（舊做法） | 約 255 ms；會經過輸入法 | 淘汰 |
| osascript ＋ System Events 點選單 | 177–195 ms；不經輸入法，但選單名稱跟介面語言綁死 | 不採用（仍要啟動 osascript） |
