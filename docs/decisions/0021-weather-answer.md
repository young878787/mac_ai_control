# 0021 天氣直接回答：開網頁或回答由規則決定、氣象署→Open-Meteo 備援、常問縣市

- 狀態：採用（第 1 條的「句首的搜尋 → open」被 [0023](0023-query-routing.md) 取代；第 2 條的句首、第 5 條的預設順序被 [0024](0024-home-city-and-answer-timeout.md) 修改）
- 日期：2026-11-23
- 來源：[計畫書](../plans/completed/2026-11-21-web-answer.md) §2（W1、W5～W9、W13～W18、Q14）、§4.1、§4.6、§4.7；使用者 2026-11-21、2026-11-23 的決定

## 背景

「查一下台北天氣」原本一律開 Google 搜尋頁，「台北天氣」「會下雨嗎」不命中 Fast Path、交給 LLM（可能開網頁、也可能憑記憶亂答）。天氣是高頻、有結構化資料來源的問題，使用者要的是答案，不是結果清單。

## 決定

1. **一句話只有一種結果：開網頁，或在泡泡直接回答，不同時做。**由純函式 `fast_path.answer_mode(utterance)` 依說法決定，LLM 不決定。順序：明說要看畫面（瀏覽器、Safari、Chrome、網站、網頁、Google、上網、網路上、給我看、顯示、「在 X 搜尋」、句首的搜尋）→ open（**「句首的搜尋」被 [0023](0023-query-routing.md) 取代**：搜尋＋問句、會變的事實、天氣改成直接回答）；問句或要求告知（嗎、幾、多少、怎麼、告訴我…）→ answer；說了高頻類別（目前只有天氣）→ answer；其餘（查周杰倫）→ open（現況）。兩種線索同時出現時開網頁優先（明說優先，同 [0006](0006-front-window-target.md)）。
2. **天氣窄規則 `_r_weather`**：整句要完全符合「（查／告訴我…）（縣市）（時間）（縣市）（的）主題（時間）（語尾）」才命中，產生 `get_weather(city, day, part)`；`city` 空字串＝用常問的縣市。主題分兩種：strong（天氣、會不會下雨、下雨嗎、下雨機率、氣溫、溫度）單獨就算；weak（幾度、多少度）一定要同時說了縣市或時間。「下雨」一定要帶疑問（嗎、會不會、機率）：「明天會下雨」可能是敘述，不收。（**被 [0024](0024-home-city-and-answer-timeout.md) 修改**：句首可以先有語氣詞，例如「那幫我查明天天氣」；「我住 X」開頭接天氣也收。）
   - 這條規則是 [0007](0007-no-model-for-negation.md)「提問不走 Fast」的**例外，只豁免提問這一關**：規則放在 `_blocked` 之後、`_r_open_search` 之前，所以否定、敘述（不要查天氣、昨天天氣很好）仍然被擋下、不呼叫任何模型。計畫 W9 原寫「在 `_blocked` 之前」，實作改成之後，比原計畫更嚴。
   - 不收：打開天氣（開 App）、天氣之子是什麼電影、今天天氣好熱、兩個不同的縣市或時間、後天／週末／下週（超過 36 小時）。這些維持現況（走原本的搜尋規則或交給 Slow Path）。明說要看畫面的句子（`answer_mode`＝open）也不收。
   - 只讀資料、不改變電腦狀態，誤觸發的代價是多一則回答。`match()` 保持純粹：不碰網路、資料庫、子程序，也不看金鑰。
3. **資料來源只有兩個，失敗閉環**（`weather_client.lookup`）：有 `CWA_API_KEY` 先查中央氣象署（`opendata.cwa.gov.tw`，F-C0032-001）；沒有金鑰、失敗、逾時、或這個說法在氣象署的 36 小時資料裡找不到時段（例如凌晨問明天、中午問明晚）→ 改查 Open-Meteo（免金鑰、開源）；再失敗回 `❌ 查不到`，**不開網頁**（使用者 2026-11-23 決定，取代計畫 W4 的「開搜尋頁並回 ⚠️」）。每個來源各自逾時 `WEATHER_TIMEOUT_S`＝2 秒，最差兩個都逾時約 4 秒會擋住下一句。兩個來源先整理成同一種 12 小時時段（白天 06–18、晚上 18–06；Open-Meteo 的逐時資料在本機彙總，降雨機率取最大、溫度四捨五入、天氣取最常見，下雨的小時 ≥ 3 才以降水天氣為準）再套同一個固定模板，回覆結尾標示來源（氣象署、Open-Meteo）。不經過 LLM。
4. **金鑰比照 [0010](0010-cloud-key-handling.md)**：只在 `weather_client` 經 `config.env_value("CWA_API_KEY")` 讀，放請求標頭（`Authorization`），不放網址、不進 `os.environ`、log 或錯誤訊息；錯誤只留分類（timeout、http_500…）。Open-Meteo 只收到縣市代表座標（縣市政府所在地），氣象署只收到縣市名稱。Open-Meteo 免費版限非商業用途（個人助手符合）、資料需標示來源（回覆結尾已標）。
5. （**被 [0024](0024-home-city-and-answer-timeout.md) 修改**：預設順序改成明說 → 居住地 `profile.home_city` → 統計常問 → 冷啟動；冷啟動後下一句只說縣市就接著回答並記成居住地。）**預設地點＝資料庫統計的常問縣市**：沒說縣市時，執行階段在 `command_worker` 執行緒由 `weather_prefs.default_city` 決定：最近 90 天明說次數最多的縣市，同票取最近問的，90 天內沒有就看全部歷史，都沒有就是冷啟動——不連網、不猜、不定位，回 `weather_prefs.COLD_START_MESSAGE`（可愛的口吻請使用者說縣市）。只記句子**明說**的縣市（不管查不查得到），用預設補上的不記（否則預設會自己越記越多、改不掉）。存在既有的 `data/music.sqlite3`，新增 migration `0002`（表 `weather_queries`，只追加）；檔名不改，內容不再只有點歌（[0019](0019-music-play.md) 第 8 條補註）。資料庫還沒準備好時，明說縣市照常回答、只是不記。統計只在本機，不送 LLM、雲端，也不進對話記憶。
6. `get_weather` 只放在 `LOCAL_TOOLS`，LLM 看不到（紅線 5）。回覆文字放進 `ctx.replies`（泡泡）；超過 `EXPAND_REPLY_CHARS`（20 字）會讓聊天室主動展開，與 `music_top` 相同。回覆前綴照紅線 11：✅ 有答案、⚠️ 冷啟動、❌ 查不到。

## 後果

- 行為變更：「查一下台北天氣」「幫我找一下台北天氣」從開 Google 改成回答；「台北天氣」「會下雨嗎」「今天幾度」從 Slow Path 改成 Fast Path 回答。要看網頁就說「搜尋台北天氣」「打開瀏覽器查台北天氣」。
- 實測（2026-11-23，計畫書 §9）：氣象署單次 p50 約 90 ms；Open-Meteo 約 845 ms；兩者都在 R1 門檻（p50 ≤ 1.0 s、p95 ≤ 2.0 s）內。22 縣市氣象署與 Open-Meteo 的明天白天最高溫差都 ≤ 1 °C。
- 資料庫版本從 1 升到 2，啟動時照 [0019](0019-music-play.md) 的流程先備份（`.bak-1`）再升級；舊版程式不認得新版資料庫。
- 長尾問題（周杰倫是誰、股價）的搜尋摘要回答還沒做（計畫 P3、P4，搜尋後端未定），那部分仍是現況。
- 回覆只有今天與明天；氣象署的 36 小時資料在凌晨或中午會缺明天或明晚的時段，這時由 Open-Meteo 補。後天、週末要等之後接氣象署的一週預報（計畫 P2 之後）。
