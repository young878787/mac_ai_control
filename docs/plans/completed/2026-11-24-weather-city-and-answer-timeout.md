## 0. 結論

1. **天氣城市記不住**：資料庫 `weather_queries` 至今 0 筆。只有 Fast Path 的天氣窄規則會記縣市，而使用者自然的回答（我住台北、我住台北幫我查台北的天氣、那幫我查詢明天的天氣）都不命中；冷啟動後也沒有「下一句當成縣市回答」的接續。修正內容：
   - 冷啟動後接住下一句的縣市。
   - 「我住 X」走聊天，並在背景記下居住地。
   - 「我住 X＋天氣」直接回答。
   - 天氣句首放寬。
   - 新增**常駐資料表**存居住地，居住地優先於統計。
2. **依摘錄回答逾時**：2026-11-24 實測 52 次（§7），`low` 推理單發 p50 2.29 s、p90 7.93 s，**18.4%（7/38）超過 6 秒**。
   - 7 次裡 **6 次是雲端伺服器單次請求變慢**：首位元組 4.6～6.0 s，或推理速度掉到 11～52 tok/s（正常約 122 tok/s）。
   - **1 次是推理太長**（845 tokens）。
   - 修正：`WEB_ANSWER_TIMEOUT_S` 6 → **10 秒**，試算失敗率 18.4% → 7.9%。
3. **連鎖熔斷**：依摘錄回答那次逾時，會讓整個雲端熔斷 30 秒，後面的句子都改走本機小模型。今天「我住台北」就是這樣被本機模型選成 `read_screen`。
   - 修正：**依摘錄回答那次逾時不熔斷**。
   - 連線失敗、429、5xx，以及規劃那次的逾時，照舊熔斷。
4. **預測題**（明天台股會怎麼樣）：維持走 `web_answer`（搜尋＋AI 彙總），不另加分流規則。受益於第 2、3 點。

## 1. 現況與證據（2026-11-24 log）

### 1.1 天氣

| 時間 | 語句 | 路線 | 結果 |
|---|---|---|---|
| 20:45:03 | 那幫我查詢明天的天氣 | 不命中 Fast（句首「那」）→ 熔斷中 → 本機 LLM | 只開 Google 搜尋頁 |
| 20:50:46 | 幫我查詢明天的天氣 | Fast `get_weather(city="")` | ⚠️ 冷啟動（請說縣市） |
| 20:51:01 | 我住台北 | 不命中 Fast → 熔斷中 → 本機 LLM | **`read_screen`**，9.86 s，描述螢幕（完全無關） |
| 20:59:52 | 幫我查詢明天的天氣 | Fast | ⚠️ 冷啟動（又問一次） |
| 21:00:06 | 我住台北幫我查台北的天氣 | 不命中 Fast → 雲端 `web_answer` | 搜尋摘要答出天氣（8.4 s），不是氣象署，也沒記縣市 |

根因有三層：

1. `record_city` 只在 `get_weather(city=明說)` 時呼叫（[local_actions.py:863-866](../../../mac_ai/router/local_actions.py#L863-L866)）。`get_weather` 是本機工具，LLM 看不到（紅線 5），只有 Fast Path 能觸發。
2. 天氣窄規則整句完全比對（[query_intent.py:40](../../../mac_ai/router/query_intent.py#L40)）。`_W_LEAD` 不收「那、好、嗯」等句首語氣詞，也不收「我住 X」開頭。
3. 冷啟動訊息說「跟我說一下縣市嘛…下次我就記住囉」，但沒有接續機制（不像 `sources.STORE` 的「要打開來源嗎？」）。

`match()` 實跑（2026-11-24）：

| 句子 | 子句 | Fast |
|---|---|---|
| 我住台北／我住在台中／我家在高雄／台北／台北啦 | 一句 | ✗ |
| 我住台北幫我查台北的天氣 | 一句 | ✗ |
| 我住台北，明天天氣如何 | 我住台北／明天天氣如何 | ✗／✓（但縣市還沒記，仍是冷啟動） |
| 那幫我查詢明天的天氣／好那幫我查明天天氣 | 一句 | ✗ |
| 然後明天天氣呢 | 明天天氣呢（「然後」被分句吃掉） | ✓ |

現有守門對候選句的判定：

- 「我以前住台北」被敘述守門擋下。
- **「我不住台北」沒有被擋**（`_NEG_RE` 不含這種說法），新規則要自己排除。
- 「你住台北嗎」經 `canonicalize_clause` 會變成「住台北嗎」，新規則要看原句的主詞。

## 3. 設計

### 3.1 常駐資料表（C6）

- **Migration `0004_profile`**，`HEAD_VERSION` 3 → 4。升級照既有流程：先備份成 `.bak-3`，在複本上升級，成功才換回。
  ```sql
  CREATE TABLE profile (
    key TEXT PRIMARY KEY,   -- 目前只有 home_city
    value TEXT NOT NULL,    -- 正規化後的縣市名（例：臺北市），與 weather_queries.city 同一套
    source TEXT NOT NULL,   -- said（使用者明說：我住 X）／cold_start_reply（冷啟動後回答的縣市）
    updated_at REAL NOT NULL
  )
  ```
- 新模組 `mac_ai/router/profile_store.py`：`get(conn, key)`、`set(conn, key, value, source, now)`（覆寫）。規範比照 `weather_prefs`：函式收呼叫端的連線與注入的 `now`，不自己連線，SQL 參數化，每個公開函式自己 commit。
- **只記使用者明說的**，不從統計推出居住地，也不由模型決定要記什麼（見 §5 建議）。
- 新的「我住 Y」直接覆寫舊值。設居住地時，同時照舊 `record_city` 記一筆統計。
- `get_weather` 的預設改成：`city or profile.home_city or weather_prefs.default_city or 冷啟動`（紅線 7：明說 → 預設）。
- 資料只在本機；不送雲端、不進對話記憶（維持 0021 第 5 條的精神）。C2 送雲端的只有使用者原句本身（原本就會送）。

### 3.2 冷啟動接續（C1）

- 比照 [sources.py](../../../mac_ai/router/sources.py)，新增 `mac_ai/router/weather_followup.py`：
  - 存「冷啟動時原本要問的 day、part」，只放記憶體。
  - `take()` 取出即清。
  - 有效期 `WEATHER_CITY_FOLLOWUP_TTL_S`＝60 s，與喚醒會話、來源追問一致。
- `get_weather` 冷啟動時呼叫 `put(day, part)`。
- `process_voice_command` 開頭呼叫 `take()`。句子只有一個子句、且 `parse_city_reply(clause)` 有結果時 → `Match([("get_weather", {city, day, part, set_home: True})])`。
  - `set_home` 由 pipeline 決定，`match()` 看不到待答狀態，所以這段不放進 Fast Path 規則，與來源追問相同。
- `parse_city_reply` 是純函式，放在 `query_intent.py`：
  - 整句比對 `^(語氣詞)?(我|我家|我們家)?(住|住在|在|是)?(縣市)(語尾)?$`。
  - 縣市用既有的 `WEATHER_CITY_ALIASES`。
  - 不是縣市回答 → 待答作廢，這句照平常處理。

### 3.3 「我住 X」→ 背景記錄＋聊天（C2、C5）

- 新增純函式 `_home_city(raw, s)`，放在 `classify_query` 裡、`_weather` 之前。
  - 整句比對 `^(我|我家|我們家)(現在)?(住|住在|在)(縣市)(語尾)?$`。
  - 命中後產生 `Match([("remember_home", {"city": X})])`。
- 本機工具 `remember_home(city)`：
  - `profile_store.set(home_city)`，再加 `record_city`。
  - 回 `✅ 已在背景記下居住地：{city}`，只進 log，**不放進 `ctx.replies`**（不出泡泡）。
  - 設 `ctx.escalate = {"kind": "chat", "note": "已在背景記下使用者的居住地：{city}"}`。
  - 工具只放在 `LOCAL_TOOLS`，LLM 看不到（紅線 5）。
- `_escalate_to_llm` 新增 `kind == "chat"`，同一步接著聊天，原句照原樣送出（紅線 11）：
  - **有雲端**：走既有的雲端規劃（紅線 9：雲端只用在規劃）。user 訊息末尾附 `<note>…</note>`（紅線 2：動態資訊只放 user 訊息），**丟棄所有工具呼叫，只採用 `chat_reply` 文字**。
  - **沒有雲端或熔斷中**：走本機 `chat_reply(ctx)`，`ctx.chat_hint` 帶同一段 note。不帶工具，所以不可能選到 `read_screen`。
  - 模型沒給文字或失敗：回固定句「好～記住你住{city}了，之後問天氣就查{city}喔」。
  - note 寫明「已經記下」，回覆可以自然確認，不會謊稱也不會否認（紅線 9）。
- 規則放在 `_blocked` 之後（比照 0021 第 2 條），否定、敘述守門照舊先擋。規則本身另外排除：
  - 原句含「不、沒、以前、之前、曾、嗎、？」。
  - 主詞不是我／我家／我們家（朋友、他、你）。
  - 允許語尾以外的尾巴（很多年了、的朋友說…）。
- 誤觸發清單（全部要有測試，期望不產生 `remember_home`、`get_weather`）：我不住台北、我以前住台北、我住台北很多年了、我住台北的朋友說明天會下雨、我朋友住台北、你住台北嗎、我住台北嗎、我要去台北、我明天去台中、我在台北出差、台北（沒有待答時）。
- 誤收的代價：居住地被改成錯的縣市，加一句聊天回覆，不操作電腦。說一次正確的「我住 Y」就能改回。

### 3.4 「我住 X」＋天氣（C3）

- 句首是「我住 X」、剩下的部分符合天氣窄規則 → `get_weather(city=X, set_home=True, …)`。
- 剩下的部分另有不同縣市 → 不收（交給 Slow Path）。

### 3.5 天氣句首放寬（C4）

- `_weather` 比對前先去掉句首語氣詞 `^(那麼|那|好那|好|嗯|欸|對了)(幫我)?`，再比對原本的 `_WEATHER_RE`。
- 只影響天氣這條規則，不動 `canonicalize_clause`，避免影響其他規則。

### 3.6 熔斷範圍（T1、T3）

- `cloud_client.chat(..., trip_on_timeout: bool = True)`，預設行為不變。
  - 逾時且 `trip_on_timeout=False`：只拋 `CloudError("逾時")`，不設 `_down_until`，`meta["breaker"]="skipped"`。
  - 其他熔斷情況：`meta["breaker"]="tripped"`。
- `local_actions.web_answer` 的回答呼叫傳 `trip_on_timeout=False`。

### 3.7 逾時上限（T2）

`config.WEB_ANSWER_TIMEOUT_S = 10.0`，註解寫上 §7 的實測數字與日期。

### 3.8 bench

把這次的診斷腳本整理成 `bench/web_answer_latency.py`：

- 同一組摘錄重跑 N 次，用串流拆成首位元組、推理段、答案段，印推理 token 與速度。
- 一律帶 `cache no-cache`。
- 不存檔、不印網址或摘錄（Brave 條款，紅線 10）。
- 供 §8.2 R1 驗收與之後重測使用。

## 5. 提案：讓 AI 使用常駐資料（不在本次實作，另開計畫）

使用者 2026-11-24 提到「在想怎麼讓現有 AI 記錄常駐資料、資料庫輔助」。本次的 `profile` 表就是基礎，之後要擴充時建議如下。

**1. 誰來寫：規則寫，不讓模型寫。**

- 只有 Fast Path 規則認得的明說句型才寫入，例如「我住 X」，之後可以加「我叫 X」「我的公司是 X」。
- 不讓模型決定要記什麼（不給模型 `remember_fact` 工具）。理由：
  - 模型會記錯，而且這等於多開一條寫入通道，違反紅線 5 的信任邊界。
  - 「準」優先：記錯的常駐資料會一直影響之後的行為。

**2. 誰來讀：本機程式讀，模型只在需要時看到。**

- 程式自己用的（天氣預設、之後的常用地點等）：直接讀資料表，不經模型。這次的居住地就是這樣用。
- 要讓模型知道的：放在 user 訊息的 `<profile>` 區塊（紅線 2，不能動 system prompt）。
  - 這是**新的資料流**：常駐資料會隨每次雲端請求送出，與 0021 第 5 條「只在本機」不同。
  - 建議預設只給本機模型，雲端要使用者明確同意，或只送與這句有關的鍵。

**3. 怎麼改、怎麼忘。**

- 再說一次就覆寫（我住高雄）。
- 「忘記我住哪」刪除：要再加一條規則。
- 可以說「你記得我什麼」列出全部，讓使用者看得到、改得掉。

**4. 要你決定的（開新計畫時再問）。**

- 常駐資料要不要送雲端？
- 第一批要支援哪些鍵？
- 要不要「你記得我什麼」「忘記…」這兩個指令？

## 9. 風險與假設

- **最差延遲變長**：上限 10 s 時，`web_answer` 最差約 24 s 會擋住 `command_worker`（原本約 20 s）。只發生在尾端，實測約 8～18% 的請求超過 6 s。
- **雲端真的掛掉時多等一次**：回答那次逾時不熔斷，下一句規劃最多再等 8 s 才熔斷。雲端真的掛掉時，通常規劃那次會先失敗，回答那次很少是第一個碰到的。
- **放寬守門**：「我住 X」是敘述句。誤收的代價是居住地被改錯，加一則聊天回覆；說一次正確的就能改回。仍要全數通過 A10。規則放在 `_blocked` 之後，否定、敘述守門照舊先擋。
- **聊天步驟丟棄工具**：「我住台北，幫我開 Safari」會被分成兩個子句，開 Safari 那句照常執行，不受影響。只有「我住 X」那一步不執行工具。
- **端點偵測**：「我住台北」會變成 complete，收尾從約 1.3 s 降到約 0.35 s。如果使用者說「我住台北……幫我查天氣」中間停頓，會被切成兩句；兩句各自都正確處理（先記居住地，再用居住地回答），結果一樣。
- **資料庫升級**：舊版程式不認得 user_version 4 的資料庫（與 0021 升到 2 時相同）。
- **樣本限制**：§7 只有一個晚上、52 次。伺服器速度隨時段變動大，R1 要在不同時段重測。
