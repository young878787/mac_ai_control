# 桌面角色擬人化：注視目標、聆聽專注與生命週期

狀態：**P0 完成，P1 尚未開始（等你指示）**（2026-11-20，基準 HEAD `c42692a`）。D6 已確認，驗證條件已定案（§7）；P0 工具與改前基線已完成，數字見 §12。

**檔案位置已跟著前端分層整理（S0～S4，2026-11-20）更新**：本計畫的新檔依 [桌面前端分層整理：實作計畫.md](桌面前端分層整理：實作計畫.md) §1 的分層放進 `domain/`、`renderer/animation/`、`rig/`，不再放在 `desktop/` 根目錄或 `renderer/` 平放。設計與驗收標準不變。

參考專案：`AI_VT_V2/vtuber-web-app`，是同一套 Rushia rig 的網頁版。它的分析與實測見 [live2d-idle-motion-analysis.md](../../AI_VT_V2/docs/live2d-idle-motion-analysis.md)。

## 0. 結論

1. 目標是讓角色看起來像真人，不像機器。要做三件事：
   - **自己找注視對象**：使用者、移動中的游標、點擊處、輸入框，以及閒置時的各種視線。
   - **聽到喚醒詞後專心聽**：眼神正視、動作變小。
   - **每個階段都有對應的眼神與頭身動作**，串成「潛伏 → 聆聽 → 思考 → 回應 → 等待 → 退場」的閉環。
2. **只改 `desktop/`**。後端、`ui_bus` 協定、路由、LLM、模型檔都不動；**沒有聲音、不做口型**（B1）。
3. 做法分兩部分：
   - 移植參考專案的四個 runtime：曲線與掃視、眨眼、眼皮與眉毛、參數混合器。它們已經在同一套 rig 上調過，也有實測數字。
   - 參考專案「挑目標」的邏輯原本在 Python 後端，改寫成前端的純邏輯「注意力導演」，再加上桌面專屬的目標。
4. 原生 Idle 動作的頭、身體、眼、眉改由程序接管，只保留手臂、肩、呼吸、嘴（B2）。反應動作（Nod、Shake…）播放時，程序把頭身讓給動作。
5. 驗收標準：
   - 「無機械感」沿用參考專案的指標（B3）。
   - CPU 和 fullrig03 的 R5 相同，單位改成整台電腦（B5）。
   - 聆聽的通過標準照 D6 提案（B8，定義見 §7.1 T3）。

## 1. 要解決的問題

### 1.1 現況（2026-11-20 讀程式與模型檔確認）

- **視線**：[renderer/role/app.js](../desktop/renderer/role/app.js) 出場時把游標位置換算成目標（`(cursor − 中心) / 400`），每幀以 `1 − 0.85^(dt×30)` 的比例追上去，頭跟著轉 30°×gx。**只要游標在，就一直鎖著游標**；游標停下來，就一直盯著同一點。
- **頭、身、眼皮**：由原生 Idle 動作（8 秒循環）驅動。各動作的曲線範圍（直接讀 motion3.json）：

| Nod | 0 | −11～3.2 | −0.6～0.3 | 0.78～1 | — | 0 | |

- **聆聽**：`domain/character.js` 在 `partial`（帶喚醒詞或會話中）時把 `mode` 設成 `listening`，但畫面上沒有任何不同，只多一個 partial 泡泡。

### 1.2 機械感從哪裡來

| 現象 | 原因 |
|---|---|
| 頭身動作每 8 秒重複 | 只有 Idle 一條固定曲線（基線實測：位置自相關 r ＝ 0.98、延遲 8 s，§12.2） |
| 眨眼節拍固定 | Idle 裡固定在 2.3 s、6.1 s |
| 眼睛像被游標拴住 | 一直鎖游標；沒有掃視、沒有失去興趣 |
| 跟游標時眼睛是滑過去的 | 游標視線用指數平滑，沒有 40～80 ms 的掃視；注視時也沒有微掃視。Idle 曲線本身的眼動是快的（90% 到位中位 90 ms），但每 8 秒一輪完全相同（每輪 6 次，§12.2） |
| 臉凍住 | 沒有眼皮、眉毛的細微變化；`BrowForm`／`BrowAngle` 沒有任何東西驅動 |
| 聽和不聽一樣 | 聆聽沒有對應的演出 |
| 想事情和閒著一樣 | 執行中只播 Curious，視線不變 |

## 3. 已確認的前提

### 3.1 模型參數

- `ParamBrowLForm`／`RForm`／`LAngle`／`RAngle` 沒有任何檔案驅動，可以給眉毛微動用。
- `ParamEyeBallForm` 是物理輸出（EyeJelly）。參考專案的「瞳孔呼吸」會寫這個參數，和物理互相覆蓋，**不移植**。
- `ParamBaseY` 只有 Surprised 用到，第二版的「跳一下」可以用它。
- 參數範圍：AngleX ±45、AngleY ±30、AngleZ ±30、BodyAngle ±10、EyeBall ±1。

### 3.2 幀率與 CPU

- 出場時本來就一律 60 fps；O5 開著時 Core 以 30 Hz 計算。潛伏時物理收尾後停格。
- 游標位置只在出場時由 [main/role-window.js](../desktop/main/role-window.js) 每 33 ms 送一次。
- 所以程序層**只增加每幀的計算，不增加出幀數**。推估每幀 < 0.1 ms，**未量測**。
- 現況出場的每秒峰值是 38.1～42.0%（單核），也就是整台電腦 4.8～5.25%（fullrig03 §13.5）。B5 的門檻正好落在現況分佈的上緣。

### 3.3 參考專案的模組與實測

## 4. 設計

### 4.1 每幀順序（只在計算幀，O5 開著時是 30 Hz）

```
1. 參數重設為預設值
2. motionQueue：Idle 或反應動作
3. 程序層（新）：注意力導演 → 曲線（ambient）→ 眨眼與臉部 → 混合器寫入
                 依 §4.3 決定每個參數聽誰的
4. expressionQueue：Multiply／Add 疊在程序層之上，happy 的眼睛 ×0.9 照樣有效
5. gestureQueue
6. 潛伏歪頭、進退場傾斜（現有，最後疊加）
7. 物理 → core.update()
```

舊的游標視線（`gx`／`gy` 與 `add(P.angleX, 30 * gx)` 那段）移除，改由程序層處理。

### 4.4 注意力導演：情境與優先順序

數字小的優先；高優先的情境結束後，才回到低優先的情境。

| 優先 | 情境（觸發） | 看哪裡 | 頭身 | 臉 | 結束 |
|---|---|---|---|---|---|
| 1 | **聆聽**：`snapshot.mode === 'listening'` | 正視使用者，只留微掃視 | 目標收斂到正前方（保留目前偏移的 60%，再加 ±0.065）；每次聆聽只歪一次小頭（headZ ±0.1～0.2）；漂移 ×0.35 | 眨眼間隔 2～5 s；眼皮只做淺的放鬆 | `mode` 離開 listening。收到 `heard` 而且是 `command` 時，先輕點一下頭表示收到（§5） |
| 2 | **打字**：輸入框開著，而且 2 s 內有打字 | 輸入框（視窗下方） | 頭微低 | — | 停打 2 s 改看使用者；輸入框關閉 |
| 3 | **點擊**：點到角色 | 點擊的位置 | 頭跟 30～45% | — | 0.8～1.2 s |
| 4 | **思考**：`mode === 'executing'` | 0.3～0.6 s 後往上側看（左右隨機），每 1～2 s 在那一帶小幅掃視 | 頭微抬、往同側歪；2.5 s 後托腮（現有手勢） | — | `result` 到達 |
| 5 | **回應**：`result` 之後，反應動作播放中 | 看使用者。Talk 開頭先移開 0.3～0.5 s，再看回來 | 讓給反應動作（§4.3） | — | 動作回到 Idle 之後再 1～2 s |
| 6 | **游標**：明顯移動（§4.5） | 游標：眼睛先動，頭跟 30～45% | — | 大幅轉移時可能順便眨眼 | 游標靜止 1.5～3 s |
| 7 | **閒置**：出場、沒有上面任何情境（會話等待、點擊或打字之後） | 劇本：`rest_front`、`glance_aside`、`look_down`、`think_up`、`weight_shift`、`curious_tilt` | 劇本決定 | 眨眼 1～4 s；眼皮、眉毛事件每 3～7 s | — |
| — | **潛伏**：`pose === 'peek'` | 回中性 | 回中性，漂移與事件全停 | 不眨眼 | 出場 |

- 劇本、權重、冷卻、「眼先動 → 頭身跟 → 看回使用者」的步驟都沿用 `avatar_runtime.py`。`hum_sway`、`hop`、`stretch` 第一版不出現（B6）。
- 潛伏時程序層停住，**不能讓停格延後**：退場後仍要在 `ui_perf` 的期限（5.8 s）內停格（§7.2 R4）。

### 4.5 游標（B4）

- 換算方式和現在相同：游標的視窗座標除以 400 px，限制在 ±1。
- **被吸引**：0.5 s 內累計移動 ≥ 60 px。
- **追視**：游標離目前注視點 ≥ 0.08（正規化），而且距離上次掃視 ≥ 150 ms，就再掃視一次。也就是用一連串小跳追，不是平滑黏著。
- **失去興趣**：游標靜止（0.3 s 內移動 < 8 px）持續 1.5～3 s（隨機），就回到閒置劇本。
- **冷卻**：失去興趣後 2 s 內，游標再動也不理，避免一直來回。
- 聆聽、打字、點擊、思考、回應期間都不理游標。

### 4.6 聆聽專注

聽到喚醒詞時，`partial` 帶 `wake`；會話中任何 `partial` 也算。

1. 下一個計算幀就開始掃視回正中（掃視 40～80 ms），頭身同時開始回正（約 0.9～1.5 s）。
2. 聆聽期間：
   - 不跑閒置劇本，不理游標。
   - 漂移縮小到 35%。
   - 眨眼變少，眼皮只做淺的放鬆。
   - 不嘟嘴、不 wink（第一版本來就沒有）。
3. 收到指令（`heard`，status 為 `command`）：輕點一下頭，接著進入思考。
4. 被忽略（`heard`，status 為 `ignored`）：回到閒置。

### 4.7 生命週期

```
潛伏（停格）
  →[partial 帶喚醒詞]→ 出場＋Surprised → 聆聽（正視、安靜）
  →[heard command]→ 輕點頭 →[executing]→ 思考（視線上移；2.5 s 後托腮）
  →[result]→ 回應（Nod／Shake／Talk；看使用者，Talk 開頭先移開一下）
  → 會話等待：閒置劇本，游標動了會看
  →[partial]→ 聆聽 …
  →[session 0]→ sleepy → 退場 → 程序層回中性 → 物理收尾 → 停格
點角色：看點擊處 → 現有的點擊反應
打字：看輸入框
```

## 9. 風險與已知限制

- **CPU 在門檻邊緣**：現況出場峰值是整台電腦 4.8～5.25%，B5 是 5.0%。程序層再小，也可能讓 R4 不過；不過時由使用者決定。
- **手臂仍是 8 秒循環**：頭身眼不再重複，但 Idle 的手臂還是 8 秒一輪，可能仍看得出規律。根治要等程序化手臂，或修改模型的 Idle 動作（第二版或之後）。
- **頭和手臂不同步**：Idle 原本頭、手臂是一起設計的，拆開後是否不協調要目視（U2）。
- **轉頭視差淺、大角度可能破圖**：參考專案在同一系列 rig 上量過，轉頭時五官在髮框裡滑動、層次淺（參考分析 §4.3）。fullrig03 是否改善**未量測**（U5）。
- **O5 的取樣粒度**：Core 以 30 Hz 計算時，40～80 ms 的掃視只有 1～2 個計算幀，眨眼約 3～6 幀，可能顯得較鈍（U7、R2）。
- **常數是在舊 rig 上調的**：眉毛增益、角度上限、`TILT_FACE` 的方向，換到 fullrig03 都要目視。
- **頭動得更多，物理也更活躍**：頭髮、緞帶、袖子會擺得比較多。出場時本來就是 60 fps，CPU 沒有影響；潛伏時程序層停住，不影響停格（R4 驗證）。
- **游標可能讓人分心**：只在出場時有效（會話 60 s、閒置 15 s 後退場），而且有冷卻。
- **RSS**：fullrig03 最近一次量測新舊版都超過 700 MB（fullrig03 計畫 §13.5，原因未查），R4 可能因為和本計畫無關的原因不過。
- 模擬指標（T2）不含反應動作、表情和 O5 內插，所以真實環境另外有 R2。
